# Create or Update PR

## Trigger

After the user says "pushed" (or similar), check whether a PR already exists:

```bash
gh pr view --json number,url,body 2>&1
```

- PR exists → offer to update the body
- No PR → offer to create one

Always ask before acting. Never update silently.

## PR Body Structure

### Required sections

**Why this PR exists**
One or two sentences. State the problem or gap being addressed — not what the code does, but why it needed changing.

**What changed**
Bulleted list of the meaningful changes. Factual, no filler.

**ACs met** (when the PR closes or advances a ticket with acceptance criteria)
Check off each AC this PR satisfies. Reference the ticket if relevant.

**Evidence** (when applicable)
Link or embed supporting proof:
- Datadog traces / APM screenshots for performance or observability changes
- Screenshots for UI or behaviour changes
- Script output for smoke-test results
- Before/after JSON or wire format for structural changes (see format below)

### Before/after format

Use when a wire format, JSON shape, field name, or caller-visible behaviour changed:

```
**Before**
\`\`\`json
{ "oldField": "value" }
\`\`\`

**After**
\`\`\`json
{ "newField": "value" }
\`\`\`
```

Separate multiple logical changes with `---`.

### Footer

Always include a ticket link when one exists:
```
Relates to [SPOT-XXXXX](url)
```

## Style rules

- Imperative mood, concise — reviewers read on a deadline
- Scannable: short paragraphs, bullets over prose
- No AI attribution (`Generated by`, `Co-authored-by`, etc.)
- No filler openers ("This PR...", "In this change...")
- Evidence is optional but expected for behaviour/performance changes

## Never include

- Internal implementation details reviewers don't need
- Redundant restating of the diff
- AI tool references of any kind
